Community OpenWrt builds for Cambium Networks enterprise Wi-Fi access points (cnPilot and XV/XE series). Each build is upstream OpenWrt main with a small, reviewable stack of Cambium hardware patches on top, rebuilt automatically every day.

The aim is to keep capable enterprise access points useful on open, maintained firmware, managed by OpenWrt directly or by an OpenWISP controller. This project is not affiliated with or endorsed by Cambium Networks.

Development snapshots. Images are built and checked automatically but are not tested on hardware for every build. Only the models marked validated below have run on real hardware. Always keep a way back to the stock firmware.

Downloads

Each snapshot is a GitHub release with one recovery and one persistent image per family, the family ImageBuilder and checksums, plus select-config.sh and cambium-manifest.json: a machine-readable list of every model, SKU, FIT configuration, validation status and image (with SHA-256) in that snapshot. The matching package feed (kernel modules and Cambium packages) is served from this site and is already configured in each image.

Supported hardware

Access points are grouped by Cambium's hardware families. Each family image contains the device tree of every model in it and boots the one that matches the access point's board SKU, so there is exactly one recovery and one persistent image per family. Families are listed oldest first. The stock firmware column is the latest published Cambium version, which should be running before an install. Sysupgrade is whether an installed OpenWrt can be upgraded in place with sysupgrade (from LuCI, the command line or OpenWISP); where it cannot, upgrade by reinstalling the persistent image.

Untested models: RAM boot only. Models in a family do not always share a flash layout, so on any model not marked validated use only the recovery (RAM) image, then send a hardware report. How it works

Two images per family

Recovery is a RAM-only image: it boots from memory, writes nothing, and a power cycle returns the access point to its stock firmware. Use it to check that a model works before installing anything. Persistent is installed into the access point's inactive firmware slot. Cambium access points keep two firmware slots; OpenWrt only ever uses one of them, and the stock firmware stays intact in the other as a fallback.

No Cambium files are distributed

The radios need a Wi-Fi board file from Cambium's firmware. These images do not include any. On first boot, the access point copies the board file its own stock firmware uses from the retained stock slot, read-only. Radio calibration is read from the access point's own calibration partition as usual. Neither is ever modified. If the stock slot is missing, the radios stay off and wired networking still works.

Safe boot

On every family, each boot of a newly installed image is a one-off: until the access point has come up healthy (network, and radios where validated), the next reboot returns to the stock firmware. Only a healthy system arms OpenWrt as the default, so a failed install recovers itself with a power cycle.

Defaults

  • Stock OpenWrt login: no SSH keys are included and root has no password until you set one.
  • The LAN port is a DHCP client. The access point never serves DHCP or router advertisements onto your network.
  • The hostname is the stock firmware's: the model and the last six hex digits of the access point's MAC address, e.g. E410-ABABAB or XV2-21X-BEA5BE.
  • Persistent images include LuCI, WPA-Enterprise (wpad-mbedtls), 802.11r/k/v roaming (usteer), WireGuard, OpenVPN, LLDP and the OpenWISP agents. Anything else can be added from the package feeds.
  • The LAN bridge filters VLANs: the LAN ports carry only untagged VLAN 1, the management network (br-lan.1), so tagged traffic on the same trunk cannot swamp DHCP. OpenWISP's device template adds tagged VLANs where they are wanted.
  • The status LED is blue while the access point's OpenWISP controller answers it, and green otherwise, on every family.
  • /etc/openwrt_release shows the upstream OpenWrt version; /etc/cambium-openwrt-release records the family build ID and source commits.

Installing

Read first. Everything is done from a root shell on the stock firmware: the models ported so far have no interactive U-Boot prompt, so there is no serial-console route to boot an image. A serial console is still useful for watching boot messages. Back up everything before writing anything, and never erase or overwrite the bootloader, U-Boot environment or ART (calibration) partitions.

Overview

  1. Get a root shell on the stock firmware. Cambium's firmware protects its root shell with a per-device challenge and unlock code. The tool that answers it is not published; please open an issue to ask about access. Every later step runs in this root shell.
  2. Use the installer for the steps below: one command each, with every check built in.
  3. Check the model and slot. Confirm the board SKU and which slot the stock firmware runs from (below). Stop if either is not what your family expects.
  4. Back up the inactive firmware slot, the U-Boot environment and the ART partition, and copy the backups off the access point.
  5. RAM-boot the recovery image through a self-restoring one-shot boot command. The stock firmware slot is not touched; the next reboot or power cycle returns to it.
  6. Untested model? Stop here and send a hardware report from the booted recovery image. Everything after this step is for validated models only.
  7. Install the persistent image into the inactive slot, boot it once, check it, then make it the default.

The installer: one command per step

cambium-install.sh (from the release, or this site) runs the procedures below for every family from the stock firmware's root shell: it identifies the model, checks the flash layout, running slot and boot environment, fetches and verifies the images against the release checksums, backs up what it will touch, writes, reads back and arms the self-restoring boot. It writes nothing until every check has passed and you add --yes, and it stops at the first problem with the exact reason (the failing command, its exit status and its error) and a log in /tmp/cambium-install/install.log.

On your computer, put every release file in one folder (images, SHA256SUMS, select-config.sh, cambium-install.sh and cambium-serve.py) and serve it over http (the stock firmware's wget may not do https). cambium-serve.py also receives the backups the installer uploads, into an uploads folder, so you never need the stock firmware's root password:

cd cambium                              # the folder with the release files
python3 cambium-serve.py 8000

On the access point, fetch the script and do a check run. It backs up what it will touch, uploads the backups to your computer and checks each upload's SHA-256, but writes nothing to flash:

wget -O /tmp/cambium-install.sh http://COMPUTER_IP:8000/cambium-install.sh
sh /tmp/cambium-install.sh --from http://COMPUTER_IP:8000 ram      # checks, backs up and uploads the backups; writes nothing

Check the backups are in uploads/ on your computer, then run it for real; it reboots into OpenWrt once:

sh /tmp/cambium-install.sh --from http://COMPUTER_IP:8000 --yes ram

Use cambium-serve.py, not a plain python3 -m http.server: a plain server cannot receive the backups, and the installer stops and says so. If you must use one, copy /tmp/cambium-install/backup/ off yourself and add --backed-up. A TFTP server that accepts uploads also works with --tftp COMPUTER_IP (Sage's RAM boot always needs --tftp: its U-Boot loads the image from that server as sage-recovery.itb).

The per-family steps below are what the script does, for reference and for doing it by hand.

Common steps (stock firmware root shell)

Copy images to the access point's /tmp from a TFTP server on your network, then check them against the release's SHA256SUMS:

tftp -b 8192 -g -l /tmp/IMAGE -r IMAGE SERVER_IP
sha256sum /tmp/IMAGE

Before you start: latest stock firmware, ideally in both slots

Update the access point to the latest published Cambium firmware for its family (the Stock firmware column in the hardware table; these are the versions the procedures were validated on). Ideally install it twice: each Cambium upgrade writes the slot that is not running and then switches to it, so a second upgrade leaves the same current version in both slots. The slot OpenWrt does not use keeps a current stock firmware for rollback, and it is where OpenWrt reads the Wi-Fi board file from.

First: which slot is the stock firmware running from?

Every access point has two firmware slots. OpenWrt is only ever staged and installed in the slot the stock firmware is not running from, so establish that before anything else:

od -An -tx1 /proc/device-tree/cambium-platform/board-sku   # hex SKU, e.g. 00000013 = 19 (XV3-8)
fw_printenv image                         # the slot U-Boot booted
cat /proc/cmdline                         # ubi.mtd=... or root=ubi0:rootfsN names the running slot
cat /proc/mtd                             # partition numbers and names
cat /sys/class/ubi/ubi0/mtd_num           # the MTD of the running slot

Selecting the FIT configuration

Each boot command must name the FIT configuration for the exact model. Rather than choosing it by hand, copy select-config.sh (from the release, or this site) to /tmp on the access point. It reads the board SKU and prints the model and configuration for the image you are about to boot, warns if that model is untested, and prints nothing (so the boot commands below write nothing) for an unknown SKU or an image that is not built for the model:

sh /tmp/select-config.sh recovery     # or installer, persistent

The command blocks below run it for you. Check the printed MODEL is your access point before rebooting. The table at the end lists every configuration.

Untested models: RAM boot and send a report

On a model that is not validated in the hardware table, do only this: collect a report on the stock firmware, RAM-boot the recovery image with your family's steps below, collect a report in the booted image, and open a Cambium hardware report issue with both files attached. Do not install the persistent image. cambium-report.sh (from the release, or this site) only reads: it never writes flash or the U-Boot environment and copies no firmware, calibration or board-data contents. It masks MAC addresses (keeping the vendor half) and serial numbers; read the file before posting it.

On the stock firmware, first, so the flash layout is known even if the RAM boot fails:

tftp -b 8192 -g -l /tmp/cambium-report.sh -r cambium-report.sh SERVER_IP
sh /tmp/cambium-report.sh                      # writes /tmp/cambium-report-sku*.txt
cd /tmp && for f in cambium-report-sku*.txt; do tftp -p -l "$f" -r "$f" SERVER_IP; done

If your family's steps below find a partition layout that differs from the one they expect, stop there: do not stage or RAM-boot anything, and send the stock-firmware report.

In the booted recovery image (OpenWrt in RAM; the LAN port takes an address by DHCP and root has no password), from your computer:

scp -O cambium-report.sh root@AP_IP:/tmp/
ssh root@AP_IP sh /tmp/cambium-report.sh
scp -O 'root@AP_IP:/tmp/cambium-report-sku*.txt' .

Also note in the issue whether each Ethernet port linked and got an address, what the LEDs did and whether the radios came up. A serial console log of the boot is very welcome. Rebooting or power cycling returns the access point to the stock firmware.

Sage — validated on the E410 and E410B (stock firmware 4.2.3.3)
E410 and E410B only. The backup, install and commit commands below write raw UBI volumes laid out as on the E410/E410B, and the commit helper refuses any other model. The E510 shares that layout but has not been installed yet; the E600, E700, E430W and E430H use a different NAND controller. On those models, use only the recovery (RAM) trial and send a report.

The stock firmware runs from slot image=0 or 1; OpenWrt goes into the other one. The examples assume image=0, so slot 1 (/dev/ubi0_2 kernel, /dev/ubi0_3 root) is written. For image=1, use /dev/ubi0_0//dev/ubi0_1 and swap 0 and 1 in the commands.

Back up the environment and the inactive slot:

dd if=/dev/mtd5ro of=/tmp/appsblenv.bin
dd if=/dev/mtd7ro of=/tmp/art.bin
dd if=/dev/ubi0_2 of=/tmp/oem-linux1.bin bs=126976
dd if=/dev/ubi0_3 of=/tmp/oem-rootfs1.bin bs=126976
sha256sum /tmp/*.bin    # copy all four files off the AP

RAM boot. Sage U-Boot loads the recovery image over TFTP. Put ...sage-recovery-initramfs-zImage.itb on your TFTP server as sage-recovery.itb. The command restores the stock bootcmd before trying anything:

CONFIG=; eval "$(sh /tmp/select-config.sh recovery)"; echo "MODEL=$MODEL CONFIG=$CONFIG"
fw_setenv ipaddr AP_IP
fw_setenv serverip SERVER_IP
[ -n "$CONFIG" ] && fw_setenv bootcmd 'setenv bootcmd bootipq; saveenv; tftpboot 0x84000000 sage-recovery.itb && bootm 0x84000000#'"$CONFIG"'; bootipq'
fw_printenv bootcmd
sync; reboot

Install. Copy ...sage-persistent-squashfs-kernel.itb and ...sage-persistent-squashfs-rootfs.ubifs to /tmp, write them into the inactive pair and read them back:

CONFIG=; eval "$(sh /tmp/select-config.sh persistent)"; echo "MODEL=$MODEL CONFIG=$CONFIG"
[ -n "$CONFIG" ] &&
ubiupdatevol /dev/ubi0_2 /tmp/KERNEL.itb &&
ubiupdatevol /dev/ubi0_3 /tmp/ROOTFS.ubifs
sync
head -c "$(wc -c < /tmp/KERNEL.itb)" /dev/ubi0_2 | sha256sum    # must match KERNEL.itb
head -c "$(wc -c < /tmp/ROOTFS.ubifs)" /dev/ubi0_3 | sha256sum  # must match ROOTFS.ubifs
fw_setenv owrt_trial_slot 1
fw_setenv owrt_fallback_slot 0

Arm a one-shot trial of slot 1 that saves the stock slot as the default first:

CONFIG=; eval "$(sh /tmp/select-config.sh persistent)"; echo "MODEL=$MODEL CONFIG=$CONFIG"
[ -n "$CONFIG" ] && fw_setenv bootcmd 'setenv bootcmd bootipq; setenv image 0; setenv bootcount 0; saveenv; setenv image 1; setenv bootargs "mtdparts=spi0.1:128M(fs) ubi.mtd=fs root=ubi0:rootfs${image} rootfstype=ubifs rootwait"; nand device 1 && setenv mtdids nand1=nand1 && setenv mtdparts "mtdparts=nand1:0x8000000@0x0(fs)" && ubi part fs && ubi read 0x84000000 linux${image} && bootm 0x84000000#'"$CONFIG"'; setenv image 0; bootipq'
fw_setenv image 0
fw_setenv bootcount 0
fw_printenv bootcmd
sync; reboot

Commit. In OpenWrt, set a root password, check the LAN and both radios, then keep OpenWrt with the stock slot as fallback:

passwd
sage-migration-mark-good --confirm

Until then, any reboot returns to the stock firmware. To go back later: sage-migration-rollback-oem --confirm-oem, then reboot. Later upgrades use sysupgrade.

Thor — XV3-8 (stock firmware 7.2-r1). Not for the XE5-8.

The Thor persistent image is the A/B build: two OpenWrt banks, with sysupgrade writing the inactive one and automatic rollback, as on Jaguar and Cheetah. Its FIT has one configuration per bank (config@hk02 for rootfs, config@hk02-bank1 for rootfs_1). The earlier single-bank image was validated on the XV3-8; the A/B build has not run on hardware yet, so the install needs --trial.

OpenWrt goes into rootfs, so the stock firmware must be running from rootfs_1 (UBI device 0 on mtd2); if it runs from rootfs, upgrade the stock firmware once more first. Thor U-Boot has no working network, so RAM images are staged in an openwrt volume in rootfs; its default command is aq_load_fw&&bootipq and it rejects any other bootcmd unless changing_bootcmd=1 was saved first. The installer handles all of this.

Do not install on the XE5-8: its flash layout has not been captured.

RAM boot

sh /tmp/cambium-install.sh --from http://COMPUTER_IP:8000 ram        # check run; writes nothing
sh /tmp/cambium-install.sh --from http://COMPUTER_IP:8000 --yes ram

Install

sh /tmp/cambium-install.sh --from http://COMPUTER_IP:8000 --trial install
sh /tmp/cambium-install.sh --from http://COMPUTER_IP:8000 --trial --yes install

With ubiformat on the stock firmware, this writes the factory image into rootfs, hashes it back and arms the guarded first boot. Without it, the installer RAM-boots once; SSH to it as root and run the same install command there. In OpenWrt, set a root password; cat /tmp/cambium-board-data.status should say vault. Convert to two OpenWrt banks as on Jaguar, with --allow-untested.

Single-bank Thor installs

An XV3-8 installed with the earlier single-bank image boots OpenWrt directly and has no device-data vault, so it cannot be converted in place. Its existing sysupgrade still installs the new image into the same bank, but to move it to A/B, reinstall it once. From its OpenWrt:

sh /tmp/cambium-install.sh --yes stock        # the stock firmware becomes the default boot; reboots

then run the install above from the stock firmware.

Jaguar — validated on the XV2-2T1 and XV2-2 (stock firmware 7.2-r1)

The Jaguar persistent image is the A/B build: two OpenWrt banks, with sysupgrade writing the inactive one and automatic rollback. On the XV2-2 and XV2-2T1 it is installed with the installer, and the XV2-2 has been converted to two OpenWrt banks and switched banks with a sysupgrade, its device-data vault intact. On the XV2-2T0, XE3-4 and XE3-4TN the install is untested and needs --trial; only trial a unit you can recover. The persistent RAM test image is only in the build's cambium-jaguar Actions artifact (test-only/, with its test-only-SHA256SUMS).

Jaguar models differ: the XV2-2 has a 128 MiB NAND with two 52 MiB banks (slot 1 at 0x3400000), the others two 96 MiB banks (slot 1 at 0x6000000). The installer checks the layout against the model and works in whichever slot the stock firmware is not running from, in either direction: the XV2-2 usually runs its stock firmware from rootfs, the XV2-2T1 from rootfs_1. Use the installer for every step below that writes flash.

RAM boot

sh /tmp/cambium-install.sh --from http://COMPUTER_IP:8000 ram        # check run: layout, slot, image hashes; backs up and uploads; writes nothing
sh /tmp/cambium-install.sh --from http://COMPUTER_IP:8000 --yes ram

On a stock XV2-2 the inactive slot's firmware copy leaves too little free space for the RAM image (23 free eraseblocks on the tested unit). The check run then says how many are free and needed; to erase that slot (it is backed up) and stage the image there, add --format-inactive:

sh /tmp/cambium-install.sh --from http://COMPUTER_IP:8000 --format-inactive --yes ram

In the booted image (DHCP on the LAN port, root without a password), run the hardware report. Any reboot or power cycle returns to the stock firmware.

Persistent RAM test

The A/B trees in RAM, with no firmware bank attached (put the test-only ...jaguar-persistent-initramfs-uImage.itb in the served folder):

sh /tmp/cambium-install.sh --from http://COMPUTER_IP:8000 --trial --persistent-test --yes ram

In it, confirm the model, that both firmware banks show the writable flag (0x400 set) and that NVRAM, crash log and ART do not. Run nothing that writes flash in it:

cat /tmp/sysinfo/board_name /proc/cmdline         # the model; no ubi.mtd= on the command line
for i in $(sed -n 's/^mtd\([0-9]*\):.*"\(rootfs\|rootfs_1\|NVRAM\|0:NVRAM\|crashLog\|crashlog\|0:ART\)"$/\1/p' /proc/mtd); do
  echo "mtd$i $(cat /sys/class/mtd/mtd$i/name) flags=$(cat /sys/class/mtd/mtd$i/flags)"; done
ls /sys/class/ubi    # nothing attached

Persistent install

Writes factory.ubi over the inactive slot, hashes its kernel and root filesystem back, and arms the guarded first boot. Until conversion, every boot first restores the stock bootcmd; OpenWrt re-arms its boot after each healthy start, and an unhealthy start returns to the stock firmware:

sh /tmp/cambium-install.sh --from http://COMPUTER_IP:8000 install                                  # check run
sh /tmp/cambium-install.sh --from http://COMPUTER_IP:8000 --yes install          # add --trial on the XV2-2T0, XE3-4 and XE3-4TN

In OpenWrt, set a root password and check the device-data vault, the guard and the radios. On this first boot the board file is copied from the stock firmware's slot into this bank's vault:

passwd
cat /etc/cambium-openwrt-release
cat /tmp/cambium-board-data.status      # vault: board file copied into this bank's vault
cambium-ab-status                        # mode=oem-fallback, running = the slot OpenWrt was installed in
logread -e cambium-ab-guard              # "healthy; guarded OpenWrt boot of slot N rearmed" within 5 minutes
iw dev

Convert to two OpenWrt banks

Images built before 25 September 2026 name the commands below jaguar-ab-convert and jaguar-ab-status; newer ones cambium-ab-convert and cambium-ab-status, the same on every family.

This replaces the stock firmware in the other bank with a copy of the running OpenWrt bank, after which the access point has no stock firmware on flash. Returning to stock then means writing your backup back, which has not been tested yet: only convert a unit you can recover, and open an issue first if unsure. From your computer, back up the stock bank as OpenWrt sees it now (it is not attached, so it does not change):

ssh root@AP_IP 'grep -q "ubi.mtd=rootfs_1" /proc/cmdline && S=rootfs || S=rootfs_1; sed -n "s/^mtd\([0-9]*\):.*\"$S\"\$/\1/p" /proc/mtd' > stock-mtd
N=$(cat stock-mtd); echo "stock firmware bank: mtd$N"
ssh root@AP_IP "cat /sys/class/ubi/ubi*/mtd_num"   # mtd$N must not be listed
ssh root@AP_IP "cat /dev/mtd$N" > jaguar-oem-bank.bin
sha256sum jaguar-oem-bank.bin
ssh root@AP_IP "sha256sum /dev/mtd$N"            # must match; keep the file safe

Then, in OpenWrt, convert with that hash:

cambium-ab-convert --oem-sha256 HASH --yes          # add --allow-untested on any model but the XV2-2 and XV2-2T1
cambium-ab-status                                   # mode=ab, confirmed = the running slot
reboot                                             # must come back on the same slot

A/B sysupgrade

sysupgrade runs the upgrade scripts of the running system, not those in the new image. An AP installed from a build before snapshot 2026.09.24 evening lacks the stage-2 fix (the first XV2-2 upgrade formatted the inactive bank and then stopped), so install the current release's Jaguar upgrade scripts on it first. The command checks, keeps the old copies and verifies the new ones load:

wget -O /tmp/cambium-install.sh http://COMPUTER_IP:8000/cambium-install.sh
sh /tmp/cambium-install.sh --from http://COMPUTER_IP:8000 update-upgrader                  # check run
sh /tmp/cambium-install.sh --from http://COMPUTER_IP:8000 --yes update-upgrader

Then upgrade. It writes the inactive bank, reads it back, and arms a one-shot trial of it; the old bank stays the default until the new one passes its checks (slot, overlay, DHCP on the LAN, device-data vault), within about five minutes of booting. If a step fails, cambium-ab-status shows the failing command, its exit status and its error in last_failure:

scp -O openwrt-qualcommax-ipq60xx-cambiumnetworks_jaguar-persistent-squashfs-sysupgrade.bin root@AP_IP:/tmp/sysupgrade.bin
ssh root@AP_IP sysupgrade -T /tmp/sysupgrade.bin     # the image check alone
ssh root@AP_IP sysupgrade -v /tmp/sysupgrade.bin     # keeps settings; add -n to reset them
ssh root@AP_IP cambium-ab-status                      # a few minutes later: running = confirmed = the new slot

Rollback. To check it on your own unit, upgrade and make the trial fail: cut the power while the new bank is booting, before cambium-ab-status would show it confirmed, or keep it from getting a DHCP lease so its health check fails and it reboots after five minutes. The access point must come back on the old bank with the failure recorded:

ssh root@AP_IP cambium-ab-status     # state=rolled-back, last_failure=..., running and confirmed = the old slot
ssh root@AP_IP fw_printenv bootcmd  # run jaguar_stableN for the old slot

Settings follow the upgrade unless -n is given, and cat /tmp/cambium-board-data.status still says vault afterwards. Please report any failure in an issue.

Cheetah — recovery validated on the XV2-21X (stock firmware 7.2-r1); A/B build untested

The Cheetah persistent image is now the same A/B build as Jaguar's: two OpenWrt banks, sysupgrade writing the inactive one, and automatic rollback. Its boot command now sets the kernel arguments for the bank, which has not yet run on hardware, so the install needs --trial on every Cheetah model for now; only trial a unit you can recover. The earlier one-OEM persistent image was validated on the XV2-21X. Cheetah's banks are 96 MiB, rootfs at NAND 0x80000 and rootfs_1 at 0x6080000; OpenWrt is installed into rootfs, so the stock firmware must be running from rootfs_1. Use the installer for every step that writes flash.

RAM boot

sh /tmp/cambium-install.sh --from http://COMPUTER_IP:8000 ram        # check run: layout, slot, image hashes; backs up and uploads; writes nothing
sh /tmp/cambium-install.sh --from http://COMPUTER_IP:8000 --yes ram

In the booted image, run the hardware report. Any reboot or power cycle returns to the stock firmware.

Persistent install

Writes factory.ubi over rootfs, hashes its kernel and root filesystem back, and arms the guarded first boot. Until conversion, every boot first restores the stock bootcmd; OpenWrt re-arms its boot after each healthy start (on the XV2-21X that includes both radios), and an unhealthy start returns to the stock firmware:

sh /tmp/cambium-install.sh --from http://COMPUTER_IP:8000 --trial install              # check run
sh /tmp/cambium-install.sh --from http://COMPUTER_IP:8000 --trial --yes install

In OpenWrt, set a root password and check the device-data vault, the guard and the radios:

passwd
cat /tmp/cambium-board-data.status      # vault: both board files copied into this bank's vault
cambium-ab-status                       # family=cheetah, mode=oem-fallback, running=0
logread -e cambium-ab-guard             # "healthy; guarded OpenWrt boot of slot 0 rearmed" within 5 minutes
iw dev

Convert to two OpenWrt banks

Replaces the stock firmware in rootfs_1 with a copy of the running OpenWrt bank; afterwards only your off-device backup can bring the stock firmware back. From your computer, back up the stock bank:

N=$(ssh root@AP_IP "sed -n 's/^mtd\([0-9]*\):.*\"rootfs_1\"\$/\1/p' /proc/mtd"); echo "stock bank: mtd$N"
ssh root@AP_IP "cat /dev/mtd$N" > cheetah-oem-rootfs_1.bin
sha256sum cheetah-oem-rootfs_1.bin
ssh root@AP_IP "sha256sum /dev/mtd$N"            # must match; keep the file safe

Then, in OpenWrt:

cambium-ab-convert --oem-sha256 HASH --allow-untested --yes
cambium-ab-status                                  # mode=ab, confirmed=0
reboot                                             # must come back on slot 0

A/B sysupgrade

The same as Jaguar: the inactive bank is written and read back, a one-shot trial boots it, and the guard commits it once healthy or the AP returns to the old bank. cambium-ab-status shows the result, and the failing command and its error in last_failure if a step fails:

wget -O /tmp/sysupgrade.bin http://COMPUTER_IP:8000/openwrt-qualcommax-ipq50xx-cambiumnetworks_cheetah-persistent-squashfs-sysupgrade.bin
sysupgrade -T /tmp/sysupgrade.bin
sysupgrade /tmp/sysupgrade.bin                     # keeps settings; add -n to reset them
cambium-ab-status                                  # a few minutes later: running = confirmed = the new slot

After the first boot (all families)

Set a root password with passwd, then check cat /tmp/cambium-board-data.status (should be vault on Thor, Jaguar and Cheetah), cat /etc/cambium-openwrt-release and the radios with iw dev. Configure the network or OpenWISP as required.

Upgrade & rollback

Upgrading

  • Sage uses the standard OpenWrt sysupgrade with the family sysupgrade.bin, from LuCI, the command line or OpenWISP, on the E410, E410B and E510 (the E410-layout models). On the E600, E700, E430W and E430H it refuses to write anything until their layout is captured. It writes the slot OpenWrt is not running from and keeps the running one as the fallback until the new image proves healthy. The first upgrade after migration therefore replaces the stock firmware; from then on the two slots alternate between OpenWrt versions. Go back to the stock firmware first if you might still want it.
  • Jaguar, after conversion to two OpenWrt banks, uses sysupgrade with the family sysupgrade.bin, on the XV2-2 and XV2-2T1: it writes the inactive bank, trial-boots it and rolls back automatically if the new bank fails its checks. See the Jaguar steps.
  • Thor and Cheetah have the same A/B sysupgrade after conversion, not yet tested on hardware; see the Thor and Cheetah steps. Before conversion, a Thor, Jaguar or Cheetah is upgraded by reinstalling the persistent image from the stock firmware (cambium-install.sh stock returns to it). An XV3-8 still on the single-bank image sysupgrades in place to the new image, then reinstalls once to move to A/B.
  • Kernel modules must come from the same snapshot as the running image. The feed for each snapshot is configured in the image; feeds for the two most recent snapshots are kept online.

Going back to the stock firmware

Until a Sage upgrade or a Jaguar conversion has replaced it, the stock firmware is still in its slot. From OpenWrt:

# Sage (after migration, before any sysupgrade)
sage-migration-rollback-oem --confirm-oem

# Thor, Jaguar and Cheetah before conversion (reboots)
sh /tmp/cambium-install.sh --yes stock

It restores the stock boot command and clears the changing_bootcmd marker. The install never changes the U-Boot image variable, so it still names the stock firmware's slot.

Safety rules

  1. Never erase or overwrite the bootloader, U-Boot environment or ART partitions. Setting individual boot variables with fw_setenv is part of the process; rewriting the partitions is not.
  2. Keep a verified backup of every unit before writing anything.
  3. On a model that is not validated, use only the recovery (RAM) image and send a report; never install the persistent image on it.
  4. Treat calibration and manufacturing data as unique to each unit; never copy them between access points.
  5. Keep the stock firmware slot intact until OpenWrt has proven itself on that model.
  6. Only RAM-boot units you can recover locally, and watch the boot on a serial console if you can.

Help wanted: hardware for validation

Every model marked untested or no build yet is waiting for a unit to test on. If you have one you could send for validation, spare, retired or faulty-but-booting, it would be most welcome: each unit tested moves a model to validated for everyone.

Please open an issue with the model and its condition, and we can arrange the details. Reports from your own units are just as welcome: RAM-boot the recovery image and send a hardware report.
